# Roadmap

## GPU-перебор на Metal

Сейчас весь перебор идёт на CPU: `ethvanity --create2` даёт ~30 млн попыток/с на M4
(10 ядер). Цель — считать на видеокарте Apple Silicon и получить сотни миллионов.

### ✅ CREATE2 / CREATE3 — сделано (`metalvanity/`)
- Swift-хост + ядро Metal, компилируемое в рантайме (Metal Toolchain не нужен).
  Аргументы и JSON — как у `ethvanity --create2/--create3`.
- M4: CREATE2 ~170 млн/с (CPU ~30), CREATE3 ~55–67 млн/с (CPU ~12).
- Каждая находка сверяется с CPU дважды: в `metalvanity` (адрес из ядра против Swift-keccak)
  и в `create2.py` (`params_address` + условие). `metalvanity --self-test` — 3×4096 адресов GPU против CPU.
- Интеграция: `create2.start_search` выбирает `metal` → `ethvanity` → Python; `--engine auto|gpu|cpu`;
  переключатель в сайдбаре; бейдж «Ускорено: Metal GPU»; `make_app.sh` собирает и кладёт бинарник.
- Что можно ещё выжать: несколько счётчиков на поток, предвычисление констант первого раунда
  (слова 7..16 блока не меняются), подбор размера батча. Полное разворачивание 24 раундов
  проверено — медленнее (145 против 176 млн/с).

### ✅ Кошельки EVM — в приложении (`metalvanity/evm/`)
Rust-хост (крейт `metal` + libsecp256k1 для стартов и перепроверки) и ядро `kernel.metal`:
поле secp256k1 на 32-битных словах, у каждого потока своя точка Q, за запуск — B точек
Q + j·G с одной инверсией на пачку (Монтгомери), keccak, сравнение по маске адреса.

- M4: ~90 млн адресов/с (холодный; MacBook Air после прогрева — 40–75) против ~2,8 млн/с у
  `ethvanity` и ~6 млн/с у keyhunt на CPU. Лучшие настройки — `--threads 16384 --batch 256`.
- Оптимизации: окно Q ± j·G (одно обратное на две точки) и отдельное возведение в квадрат — +43%
  (64 → 92,5 млн/с). Раскладка `scratch` «слово-к-потоку» для объединения доступа — без измеримого
  эффекта, не принята; держать `scratch` в threadgroup-памяти нельзя (8 КБ на поток при B = 256).
- Ограничение нагрузки: `--gpu-load 1..100` / `--max-speed` — паузы между пачками (оба GPU-движка),
  в приложении — 25/50/75/100%. macOS при паузах снижает частоту GPU, поэтому «Device Utilization»
  остаётся высоким, а скорость и нагрев падают.
- Проверка: `--self-test` (3 запуска × 32768 точек против libsecp256k1), каждая находка
  перепроверяется на CPU в хосте; на реальном поиске ключи дополнительно сверены через coincurve.
- Ключи: у каждого потока независимый случайный старт, все старты пересеиваются раз в 30 с
  (`--reseed-secs`) — ключи из одной цепочки отличаются на небольшое число, длинные цепочки
  опасны, если один найденный ключ когда-нибудь раскроют.

Интеграция (сделано): `bridge.py` выбирает GPU первым (`metalvanity-evm` → keyhunt → ethvanity → Python),
цели «начало:конец» строятся точно под пресет (`gpu_eth_targets`), поэтому пресеты на конец адреса
тоже ускоряются; ключ каждой находки ещё раз пересчитывается в адрес через coincurve; переключатель
«Считать на видеокарте» общий для кошельков и контрактов (`--engine auto|cpu`); `make_app.sh` собирает бинарник.

Сделано в 1.2.1:
- TRON на том же проходе: начало base58 — диапазон (0x41 ++ адрес), конец — sha256d-контрольная
  сумма и остатки по 2^k и 29^k (58^k = 2^k·29^k), конец до 10 символов. ~60 млн/с по началу,
  ~25 по концу. Самопроверка сравнивает находки GPU с полным перебором на CPU.
- split-key на GPU (старты P_заказчика + k·G), находки сверяются через P + k·G.
- ethvanity принимает цели «начало:конец» — условия на конец адреса работают и без GPU.

Осталось:
- «содержит» на GPU (сдвиговое сравнение по полубайтам / base58 — сложнее);
- скорость: не считать в последнем раунде keccak слова, не входящие в адрес (~+2%);
- `ethvanity` на CPU теряет много на `PublicKey::combine` (нормализация точки на каждом шаге) —
  пакетная инверсия дала бы кратный прирост и на процессоре.

### Потом — Solana и остальное
ed25519 не позволяет шагать +G по ключам (ключ выводится через SHA-512 из сида), на каждый
адрес — полное умножение на кривой. Выигрыш от GPU большой, но это отдельный движок.
